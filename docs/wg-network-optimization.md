# tutu 内网链路优化方案（设计稿，未实施）

> 状态：方案评审中。本文档只做设计，不改任何现状。
> 依据：2026-09-10 本机实测 + tutu-wg-init skill / tutu-share README 现有架构。

## 1. 现状与根因

### 1.1 实际拓扑

```text
手机A(家内WiFi+wg)          手机B(在外+wg)        外部浏览器(无wg)
      │ wg流量                  │ wg流量              │ https
      ▼                         ▼                     ▼
┌─────────────────────家 192.168.50.0/24──────────────────────┐
│ 主力机 .50.31 = wg .125.11                                   │
│   └─ share-upload:60306 / share-download:60307 【只绑125.11】│
│ 内层路由 .50.1 ──▶ 外层 .1.1 (PPPoE) ──▶ 北京联通公网        │
│        221.223.161.234（TCP海外流量被某层劫持→Vultr出口       │
│        45.78.76.220；wg 的 UDP 走联通直连，8ms 到阿里云）     │
└──────────────────────────────┬───────────────────────────────┘
                               │ UDP wg 直连 8ms，无 IPv6
                               ▼
                 阿里云 hub 47.93.242.217 = wg 192.168.125.1
                   ├─ nas.tutu.gold:443 (Tengine+雷池WAF，反代→125.11:60307)
                   └─ DNS :53
```

### 1.2 实测数据

| 路径 | 实测 | 说明 |
| --- | --- | --- |
| WiFi 链路 | 432/1153 Mbps 协商，网关 2.3ms | WiFi 不是瓶颈 |
| 联通直连 → 阿里云 | RTT 8ms，0 丢包 | 路径健康 |
| wg 隧道上传 | **~500KB/s (4Mbps)** ← 用户观察 | 痛点 |
| 联通直连下行(国内镜像) | ~1MB/s | 疑似线路本身窄，待复核 |
| Vultr 隧道路径(海外TCP) | 91Mbps↓ / 18Mbps↑ | **注意：不代表 wg 走的联通直连腿** |

> 纠错：此前诊断把 Vultr 隧道路径的 18Mbps 当成了家宽上行。wg 实际走的联通直连腿，
> 上行很可能就是 ~4Mbps——与 500KB/s 正好吻合。根因排序以此为准。

### 1.3 根因（三层，按影响排序）

1. **家内互访绕公网**：share 服务只绑 wg IP（192.168.125.11），手机人在家里也必须
   走 `WiFi → 家宽上行 → 阿里云 → 家宽下行 → 主力机`，双向穿窄上行 + 阿里云中继。
2. **联通直连腿上行窄**（~4Mbps）：一切"从家向外服务"的硬墙，拓扑怎么绕都绕不开。
3. **阿里云中继带宽 + WAF 反代加一层**：外部经 nas.tutu.gold 下载 = min(阿里云出口带宽,
   家宽上行)，两头都窄。

## 2. 目标 / 非目标

#### 目标

1. 家内互访不绕公网，跑满本地链路。
2. 家外访问自动/显式选择最快可用路径（直连 > 中继）。
3. 消除阿里云单点对"家内互访"的影响（中继仅服务外部场景）。
4. 方案长期化：一次定型，不做"先凑合以后再换"（项目约束 #7）。

#### 非目标

- 不追求提升家宽物理上行（那是运营商的事）。
- 不做多租户/复杂 ACL（个人内网，keep it simple）。
- 不做预防性抽象层（项目约束 #2）。

## 3. 分层方案

### P0：同 LAN 直连（收益最大，改动最小，先跑通闭环）

**问题**：服务只绑 wg IP，家内也绕公网。
**改法**：

- share 服务 60306/60307 由绑 `192.168.125.11` 改为绑 `0.0.0.0`；
- 防火墙放行规则：60307 允许 `192.168.50.0/24` + wg；60306 仅 wg；公网入站一律不开
  （外部仍走 nas.tutu.gold 反代）。
- `tutu-share/index.ts` 链接生成从"二选一"改为**三链接**：
  1. LAN 直链 `http://192.168.50.31:60307/<token>`（人在家）
  2. wg 直链 `http://192.168.125.11:60307/<token>`（wg 在线且异地）
  3. 公网 `https://nas.tutu.gold/<token>`（兜底）
  择优交给客户端：在家的设备连 LAN 直链即达（OS 路由天然可达，不进 wg）。

**收益**：家内传输 500KB/s → WiFi 实际吞吐（数十 MB/s 级）。
**代价**：一次服务重启 + 扩展代码小改。无新组件。

### P1：外→家直连腿（IPv6 优先，v4 端口转发备选）

**问题**：手机在外访问家内必须经阿里云中继，多一跳 + 受阿里云带宽限制。
**改法**：

- 外层光猫/路由开 IPv6（北京联通一般支持 PD 下发），主力机获全局 v6，
  wg 在 v6 上监听（hub 签发第二个 endpoint 或独立接口）；
- 家宽前缀会变 → DDNS（DNSPod API 脚本，跑主力机 cron）；
- 手机端 wg 配置加"家 v6 endpoint"，阿里云 hub 保持为中继/兜底。
- 若验证清单确认 221.223.161.234 是独享公网 v4：外层路由做端口映射是更简单的备选腿。

**收益**：外→家延迟降、阿里云故障不再阻断；但带宽仍受家宽上行 ~4Mbps 硬墙
（见 P2 策略互补）。
**多路径机制**：wg 一个 peer 只能一个 endpoint。双路径用**双接口 + 路由 metric**
（wg-home 主 / wg-relay 备，failover 脚本按 latest-handshake 切换），不做 MPTCP/bonding
（复杂度收益比差，成熟度低）。

### P2：大文件外部消费 → 云端直出（策略层，与 P1 互补）

**问题**：家宽上行 4Mbps 是物理硬墙，任何"从家向外发大文件"的拓扑都救不了。
**改法**：按消费方位置分流——

- **家内消费**：P0 的 LAN 直链（满速）。
- **家外消费**：share_upload 大文件时直接推到 hub 存储（或 OSS presigned URL），
  由**云侧带宽**直出；nas.tutu.gold 反代只服务这条腿。
- **交互性小流量**（ssh / git / 状态查询）：继续走 wg，4Mbps 完全够。

**收益**：外部下载速度 = 阿里云/OSS 带宽（可买），与家宽上行解耦。

### P3（可选，结构性替代）：Headscale / Tailscale 网格

**问题**：手工 wg 的 NAT 穿透、路径择优、多中继都要手工维护（P1 的 metric/脚本就是雏形）。
**改法**：Tailscale 协议栈 + **自托管 Headscale 控制面 + 自建 DERP（部署在阿里云 hub）**
原生解决：双层 NAT 穿透、直连优先/中继兜底、自动择优、ACL、密钥轮换。
**与 P0-P2 关系**：互斥替代——若走此路线，手工 wg 体系整体废弃、一次性切换（符合
约束 #1 不留兼容层）；P0 的 LAN 直连思想仍保留（Tailscale 本身也会走本地直连）。
**信息安全**（约束 #9）：控制面自托管、DERP 自建、流量端到端加密不经第三方。
**代价**：新组件 + 全端重配 + 125.x 地址体系迁移。**建议先落地 P0 看真实痛感再决策**。

### 条件触发项：抗 UDP QoS（治标）

仅当验证清单 #4 证实"联通对持续 UDP 限速、TCP 不限"才做（现有证据更支持
线路本身窄而非 QoS）。手段：udp2raw（UDP→伪TCP）或 AmneziaWG 混淆 wg 指纹。
不做预防性部署（约束 #2）。

## 4. 路径选择 / 负载均衡机制对比

| 机制 | 解决什么 | 复杂度 | 结论 |
| --- | --- | --- | --- |
| 服务返回多链接 + 客户端择优 | 家内/家外分流 | 低 | **P0 采用** |
| split-horizon DNS（nas.tutu.gold 家内解析到 .50.31） | 同上，域名统一 | 中 | 备选，需家内 DNS 钩子 |
| wg 双接口 + metric failover | 外→家双路径（直连+中继） | 中 | P1 采用 |
| MPTCP / 链路 bonding | 叠加带宽 | 高 | 不做（家内瓶颈不在多路径） |
| 路由器多 WAN（家宽+4G 备线） | 容灾，非提速 | 中 | 远期可选 |
| mesh 自动择优（Headscale+DERP） | 全部上述 | 中高 | P3 候选 |

## 5. 待验证清单（任一 Phase 落地前完成）

1. **外层 192.168.1.1 光猫**：管理权限？能否开 IPv6 / 端口映射 / DMZ？
2. **公网 v4 归属**：221.223.161.234 是否独享（非 CGNAT）？重拨是否变化？
   （外层路由 WAN 口状态即可确认）
3. **阿里云 hub 带宽套餐**：控制台查出口 Mbps——外部中继方向的硬上限。
4. **联通直连腿真实上下行**：hub 临时起 `iperf3 -s`，本机 TCP+UDP 各打一轮
   （区分"线路窄"还是"UDP QoS"）。
5. **45.78.76.220 归属**：哪台路由器在劫持海外 TCP？是否自有 Vultr VPS？
   若是自有，可评估作为第二中继/自建 DERP 节点（P3）。
6. **使用场景比例**：手机在家/在外的时间占比 → 决定 P1 与 P2 的先后。

## 6. 实施顺序与风险

```text
P0（当天可完成，独立收益）
 └─▶ 验证清单 #1-#4
      ├─▶ 外部消费为主 → 先 P2
      └─▶ 外部实时访问为主 → 先 P1
           └─▶ 痛点仍在/维护成本高 → 评估 P3 一次性切换
```

| 风险 | 缓解 |
| --- | --- |
| P0 绑 0.0.0.0 扩大暴露面 | 防火墙白名单（仅 50.0/24 + wg）；token 链接本身无目录枚举 |
| P1 家宽前缀漂移 | DDNS cron + wg endpoint roaming（wg 原生支持对端地址变化） |
| P2 云端存储成本 | 文件生命周期：分享即临时，N 天自动清理（服务端已有 token 机制可挂） |
| P3 迁移中断 | 一次性切换窗口，旧 wg 配置导出留档后删除，不留双轨 |
